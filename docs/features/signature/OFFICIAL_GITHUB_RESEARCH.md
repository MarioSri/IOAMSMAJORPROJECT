# Official GitHub Signing Research

## Sources reviewed

The official Documenso repository, `documenso/documenso`, describes a TypeScript and React-based signing system that uses PDF.js for viewing, PDF manipulation libraries for document output, and Playwright for end-to-end testing. Its repository documentation treats a signed document as a structured resource containing recipients, fields, and one or more PDF envelope items rather than as an image-only overlay.

The official field renderer at `packages/lib/universal/field-renderer/render-field.ts` receives the page width and height, a render scale, field metadata, and a page layer. It dispatches by field type and separates editable field rendering from signature rendering. The official signature renderer at `render-signature-field.ts` calculates field position from page dimensions, fits signature images inside field bounds without distortion, and caches image signatures at a high pixel ratio for crisp redraws. In export/sign mode it renders the inserted signature image or typed signature rather than the placeholder field label.

The browser research also reviewed Adobe Acrobat Sign’s preparation flow, Zoho Sign’s drag-and-drop signing workflow, OpenSign’s document editor, and the official `read-excel-file` and Mammoth repositories. The consistent interaction pattern is page-relative field placement, explicit field ownership, constrained resizing, zoom/rotation controls, and a distinct final-output rendering step. Mammoth explicitly warns that DOCX-to-HTML output is not pixel-perfect for complex layouts and must be sanitized before DOM insertion. `read-excel-file/browser` returns all XLSX sheets from its default export and does not support legacy binary XLS files.

## IAOMS alignment and decisions

IAOMS already uses PDF.js, Mammoth, read-excel-file, normalized percentage coordinates, field ownership, and a final signature merger. The current refinement keeps the existing UI and adds the same separation of concerns: the viewer renders a page surface, the signature engine stores page-relative normalized coordinates, and the merger produces a final signed artifact. PDF output remains a real PDF when possible. DOCX/XLSX use a sanitized rendered signed copy because the browser implementation does not mutate OOXML binaries; returning the original Office bytes as a signed artifact would be misleading.

## Continued findings

DocuSign’s official field-size guidance states that resizable fields expose corner handles, while Signature and Initials fields can also be resized through a scale percentage. It also notes that field sizing is relative to the uploaded document’s dimensions and resolution, which explains why scanned documents can make fields appear unexpectedly small. Adobe Acrobat Sign’s official preparation flow supports DOC, DOCX, RTF, XLS, XLSX, PPT, PPTX, TXT, CSV, HTML, TIFF, BMP, GIF, JPG, JPEG, and PNG; it places fields by clicking on the document or dragging them from a field panel, assigns each field to a recipient, supports signing order, and allows fields to be marked required, customized, moved, copied, cloned, or deleted.

Context7’s current PDF.js documentation confirms that a viewer should use `page.getViewport({ scale })`, size the canvas from the viewport dimensions, account for `devicePixelRatio`, and use the PDF worker configured from the installed package. PDF.js also preserves the page’s embedded rotation when rotation is omitted from `getViewport`; explicitly passing zero overrides that rotation. Context7’s read-excel-file documentation confirms that the default browser reader returns an array of `{ sheet, data }` objects for all workbook sheets and accepts File, Blob, or ArrayBuffer input. Context7’s Mammoth documentation confirms browser conversion from an ArrayBuffer to HTML and recommends treating conversion messages and generated HTML as content that requires application-side handling rather than assuming pixel-perfect Word layout.

## Vendor workflow findings from the connected browser

DocuSign’s current help page states that signature and initials fields can be resized with corner handles or a scale percentage, and that field size is affected by the source document’s dimensions and resolution. Adobe Acrobat Sign’s current help page documents support for DOC, DOCX, RTF, XLS, XLSX, PPT, PPTX, TXT, CSV, HTML, TIFF, BMP, GIF, JPG, JPEG, and PNG. Its preparation workflow places a field by clicking on the document or dragging it from a field panel, assigns it to a recipient, supports signing order, and exposes required, customize, move, copy, clone, and delete actions.

The official OpenSign repository identifies PDF e-signing as its core path and documents uploaded, typed, hand-drawn, and saved signatures, PDF templates, annotations, audit trails, and completion certificates. Its official editor guide documents four preview controls—add pages, delete pages, reorder pages, zoom in/out, and rotate pages—and supports drag-and-drop prefill widgets and signer widgets. This confirms that document navigation and field placement are separate concerns: page operations and viewport controls should not change the stored page-relative field geometry.
